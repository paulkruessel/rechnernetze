Ein Unterschied ist, dass fast kein UDP Socket einen State hat, während TCP aber mehrere Zustände hat:
\begin{itemize}
    \item \texttt{LISTEN}: Ein Dienst wartet auf eingehende TCP-Verbindungen
    \item \texttt{ESTABLISHED}: Verbindung besteht aktiv
    \item \texttt{TIME\_WAIT}: Verbindung wurde beendet, der Kernel wartet noch kurz auf Verspätete Pakete
    \item \texttt{CLOSE\_WAIT}: Gegenstelle hat geschlossen, der lokale Prozess hat den Socket aber noch offen
\end{itemize}
Dies liegt daran, dass UDP keine Verbindungen nicht selber Verbindungen verwaltet, da es verbindungslos ist.

\subsection{Bestimmen sie anhand der Portnummer und der Portliste für einige interessante/unbekannte Prozesse, mit welchem Protokoll diese kommunizieren.}

\begin{itemize}
    \item \texttt{systemd-resolve} verwendet Port \texttt{53} über TCP und UDP für DNS. Der Dienst ist an lokale Loopback-Adressen gebunden und dient als lokaler DNS-Resolver.
    \item \texttt{cupsd} verwendet Port \texttt{631} über TCP für den Druckdienst CUPS beziehungsweise IPP. Da der Dienst nur auf \texttt{127.0.0.1} und \texttt{::1} lauscht, ist er nur lokal erreichbar.
    \item \texttt{syncthing} verwendet Port \texttt{22000} über TCP und UDP für die Dateisynchronisation. Zusätzlich wird Port \texttt{21027} über UDP für lokale Geräteerkennung verwendet.
\end{itemize}


\section{Details über die Kommunikationspartner ihres PCs}

\subsection{Wie erhält das Programm die Informationen? Welcher Server wird kontaktiert? Welches Protokoll wird verwendet?}

Unter Linux wurde statt \texttt{IPNetInfo} der Befehl \texttt{whois} verwendet. Während der Ausführung von \texttt{whois} wurde mit Wireshark mitgeschnitten.

Beispiel Command:
\begin{verbatim}
whois 128.119.245.12
\end{verbatim}

In Wireshark wurde danach folgender Filter verwendet:
\begin{verbatim}
tcp.port == 43
\end{verbatim}

Dabei sieht man, dass der Rechner eine TCP-Verbindung zu einem WHOIS-Server aufbaut. Der verwendete Port ist \texttt{43}. Das verwendete Protokoll ist also WHOIS über TCP.

Die Informationen werden nicht direkt vom eigentlichen Webserver abgefragt. Stattdessen fragt der Rechner eine öffentliche WHOIS-Datenbank ab. Der Client sendet dabei die IP-Adresse an den WHOIS-Server und bekommt als Antwort Informationen wie Netzbereich, Organisation, Land und Kontaktinformationen zurück.

Für die Adresse \texttt{128.119.245.12} kam eine ARIN-WHOIS-Ausgabe zurück. Für die HTWG-Adresse \texttt{141.37.20.31} kam eine RIPE-WHOIS-Ausgabe zurück. Man sieht also, dass je nach IP-Adresse unterschiedliche WHOIS-Datenbanken zuständig sind.

address:        78462 Konstanz, Germany
route:          141.37.0.0/16
descr:          FH-KONSTANZ
origin:         AS553
\end{verbatim}

Über die HTWG findet man also, dass die Webseite unter der IP-Adresse \texttt{141.37.20.31} erreichbar ist. Diese Adresse liegt im Netzbereich \texttt{141.37.0.0/16}. Der Netzname ist \texttt{FH-KN}. Als Organisation ist \texttt{Hochschule Konstanz Technik, Wirtschaft und Gestaltung} eingetragen. Außerdem ist als Adresse \texttt{Brauneggerstr. 55, 78462 Konstanz, Germany} angegeben. Das Netz gehört zu Deutschland und wird über \texttt{AS553} geroutet.

Da die HTWG-Webseite über Port \texttt{443} aufgerufen wurde, handelt es sich hierbei um HTTPS-Kommunikation.



\section{Sockets beim Laden einer Web-Seite}



\subsection{Bestimmen Sie die Anzahl Sockets, die geöffnet werden, wenn Sie \texttt{www.spiegel.de} herunterladen.}

Für die Messung habe ich \texttt{www.spiegel.de} im Browser geöffnet und danach die externen TCP-Verbindungen gezählt.

\begin{verbatim}
paul@fedora:~$ ss -H -tan state established | grep -Ev '127\.|::1|192\.168\.178\.' | wc -l
41
\end{verbatim}

Nach dem Laden von \texttt{www.spiegel.de} waren also 41 externe TCP-Sockets geöffnet. Die Messung wurde mit aktiviertem Adblocker \texttt{uBlock Origin} und aktivierter Privacy-Protection-Erweiterung \texttt{Privacy Badger} durchgeführt. Ohne diese Erweiterungen könnten mehr Sockets geöffnet werden, da dann vermutlich mehr Werbung, Tracking-Dienste und externe Inhalte geladen werden.

Kurz zu dem Regex-Teil im Command: Mit \texttt{grep -Ev} werden Zeilen ausgeblendet, die auf den regulären Ausdruck passen. \texttt{127\textbackslash.} filtert lokale Loopback-Adressen, \texttt{::1} filtert die IPv6-Loopback-Adresse und \texttt{192\textbackslash.168\textbackslash.178\textbackslash.} filtert Verbindungen im lokalen Heimnetz.

\subsection{Was ist die maximale Anzahl von Sockets pro Remote-IP-Adresse?}

Dafür wurden die Remote-IP-Adressen gezählt und sortiert.

\begin{verbatim}
paul@fedora:~$ awk '{print $4}' socket_webseiten_analyse/01_spiegel_established.txt \
> | sed -E 's/^\[([^]]+)\]:[0-9]+$/\1/; s/^([^:]+):[0-9]+$/\1/' \
> | sort \
> | uniq -c \
> | sort -nr \
> | head -n 1
      4 2a02:26f0:480:33::212:40da
\end{verbatim}

Die maximale Anzahl von Sockets pro Remote-IP-Adresse war also 4.

Der Regex im \texttt{sed}-Befehl entfernt den Port von der Remote-Adresse. Der erste Teil ist für IPv6-Adressen mit eckigen Klammern gedacht, z.B. \texttt{[2a04:...]:443}. Der zweite Teil ist für normale IPv4-Adressen mit Port gedacht, z.B. \texttt{1.2.3.4:443}. Mit \texttt{\textbackslash 1} wird jeweils nur die IP-Adresse ohne Port ausgegeben.

\subsection{Welche Remote-Ports werden verwendet?}

Die Remote-Ports wurden aus der Liste der Verbindungen extrahiert.

\begin{verbatim}
paul@fedora:~$ awk '{print $4}' socket_webseiten_analyse/01_spiegel_established.txt \
> | sed -E 's/^.*:([0-9]+)$/\1/' \
> | sort -n -u
80
443
\end{verbatim}

Es wurden also die Ports \texttt{80} und \texttt{443} verwendet. Das passt zu HTTP und HTTPS.

Der Regex \texttt{s/\^{}.*:([0-9]+)\$/\textbackslash 1/} nimmt alles bis zum letzten Doppelpunkt weg und gibt nur die Zahl am Ende aus. Dadurch bleibt nur der Remote-Port übrig.

\subsection{Wie viele verschiedene Firmen können Sie die Remote-Hosts zuordnen?}

Die Remote-IP-Adressen wurden mit \texttt{whois} untersucht. Dabei konnten mehrere Firmen bzw. Organisationen erkannt werden.

\begin{verbatim}
paul@fedora:~$ cat socket_webseiten_analyse/06_spiegel_whois.csv
\end{verbatim}

Gefundene Firmen waren unter anderem:
\begin{itemize}
    \item \texttt{Google LLC}
    \item \texttt{Google Cloud}
    \item \texttt{Akamai Technologies}
    \item \texttt{Amazon.com, Inc.}
    \item \texttt{Microsoft Corporation}
    \item \texttt{Cloudflare, Inc.}
    \item \texttt{Fastly, Inc.}
    \item \texttt{CDN77}
\end{itemize}

Wenn man \texttt{Google LLC} und \texttt{Google Cloud} zusammenfasst, komme ich auf ungefähr 7 verschiedene Firmen.

\subsection{Laden Sie eine andere populäre Web-Seite und vergleichen Sie die Liste der kontaktierten Firmen.}

Zum Vergleich wurde eine andere populäre Webseite geladen und danach wieder die gleiche Messung durchgeführt.

\begin{verbatim}
paul@fedora:~$ ss -H -tan state established | grep -Ev '127\.|::1|192\.168\.178\.' | wc -l
49
\end{verbatim}

Für die Vergleichsseite wurden also 49 externe TCP-Sockets gemessen.

Die Remote-Ports waren wieder:
\begin{verbatim}
paul@fedora:~$ awk '{print $4}' socket_webseiten_analyse/07_vergleich_established.txt \
> | sed -E 's/^.*:([0-9]+)$/\1/' \
> | sort -n -u
80
443
\end{verbatim}

Die maximale Anzahl von Sockets pro Remote-IP-Adresse war ebenfalls 4:
\begin{verbatim}
paul@fedora:~$ awk '{print $4}' socket_webseiten_analyse/07_vergleich_established.txt \
> | sed -E 's/^\[([^]]+)\]:[0-9]+$/\1/; s/^([^:]+):[0-9]+$/\1/' \
> | sort \
> | uniq -c \
> | sort -nr \
> | head -n 1
      4 2a02:26f0:480:33::212:40da
\end{verbatim}

Die kontaktierten Firmen waren ähnlich wie bei \texttt{www.spiegel.de}, z.B. Google, Akamai, Amazon, Microsoft, Cloudflare und Fastly. Man sieht also, dass populäre Webseiten viele externe Dienste bzw. CDNs kontaktieren.
